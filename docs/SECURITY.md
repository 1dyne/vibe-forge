# 달그락 대장간 · 보안 설계

> 기준: 2026-11-04, 브랜치 `claude/compassionate-babbage-hj0l0a`.
> 이 문서는 코드가 실제로 하는 일을 적는다. 코드를 바꾸면 이 문서도 함께 고친다.

## 1. 지키려는 것

| 자산 | 누구로부터 |

| 참여자의 프로젝트 기록(아이디어, 설계, 회로, 측정값, 파일, 첨부 이미지, 제작 프로필) | 다른 참여자, 외부 공격자, **운영자 본인** |

## 2. 신뢰 경계

```

참여자 Claude ──(/api/mcp + Bearer)─┤
운영자 브라우저 ──(HMAC 쿠키)───────┤

                                   ▼
                  볼륨 /app/.data  users.json · local-projects.json · audit.jsonl
```

## 3. 운영자가 참여자 기록을 볼 수 없게 한 방법

> 2026-11-05부터 새 가입은 **이메일+비밀번호**(기본) 또는 **구글**(안내 후 동의)이다. 아래 1~7은 처음 만든 링크 방식 기준이고, 같은 원리가 §3b의 계정 열쇠로 이어진다.

**목표**: 운영자 로그인, `SESSION_SECRET`, 볼륨/백업 파일 어느 것으로도 참여자 기록이 열리지 않는다.

1. **열쇠는 참여자의 링크에만 있다.** 개인 토큰(192비트 난수)은 발급 시 한 번 보여주고, 서버에는 `sha256(토큰)`만 저장한다 (`lib/users.ts`).
2. **기록은 그 토큰으로 암호화된다.** 키 = `HKDF-SHA256(토큰, "dalgeurak-vault-v1", "owner:<id>")`, 암호 = AES-256-GCM, AAD = `project:<id>:<owner>` (`lib/vault.ts`). 볼륨의 `local-projects.json`에는 참여자 프로젝트가 `{ id, ownerId, updatedAt, sealed }` 형태로만 있다.
3. **키는 그 사람의 요청 동안에만 존재한다.** MCP 요청은 OAuth 접근 토큰(또는 예전 형식 주소의 경로 토큰)으로, 대시보드 요청은 쿠키 `u.<토큰>`으로 키를 만들고 `AsyncLocalStorage`로 그 요청 안에서만 저장소에 넘긴다 (`withVault`, `withViewerVault`). 운영자 요청에는 키가 없어서 참여자 기록은 저장소 단계에서 아예 안 보인다(접근 검사 이전에).
4. **운영자는 참여자 세션을 만들 수 없다.** 예전에는 참여자 쿠키가 `HMAC(SESSION_SECRET, userId)`라서 비밀값을 가진 사람이 아무 참여자로 로그인할 수 있었다. 이제 참여자 쿠키는 토큰 자체이고, 매 요청 해시로 확인한다. `SESSION_SECRET`은 운영자 쿠키에만 쓴다.
5. **복구 가능한 토큰 사본을 없앴다.** 예전 링크는 대시보드에 커넥터 주소를 다시 보여주려고 `SESSION_SECRET`으로 토큰을 암호화해 저장(`tokenSealed`)했다 → 운영자가 풀 수 있었다. 새 코드는 첫 실행 때 이 사본으로 기존 평문 기록을 한 번 암호화하고 사본을 지운다 (`migrateLegacy`).
6. **대화 원문은 저장하지 않는다.** 커넥터의 `record_brainstorm`·`log_team_turn`은 사용자 발화와 Claude 답변을 받지 않거나 버린다. 도구 안내가 이름·연락처·회사명을 기록하지 말라고 한다.
7. **화면·API에서도 분리.** 운영자 목록·파일 API는 `ownerId`가 없는 운영자 프로젝트만 보여준다 (`canAccess`). 참여자 관리 화면에는 별명, 가입일, 가입 경로, 연결 상태만 있다.

### 3b. 계정과 열쇠 (이메일·구글)

계정마다 무작위 **데이터 키** 하나가 기록을 잠그고(`vault.ts`), 데이터 키는 아래 "봉투" 안에만 있다(`lib/account-keys.ts`, `users.json`의 `keys`).

| 봉투 | 여는 것 | 누가 가짐 |
|---|---|---|
| `password` | 비밀번호를 scrypt(N=2^15)로 늘린 키 | 사용자만 |
| `recovery` | 가입 때 한 번 보여주는 복구 코드(약 100비트) | 사용자만 |
| `server` | `VAULT_MASTER_KEY` (구글 가입 + 안내 동의 계정만) | 서버 |

- 비밀번호 확인용 해시는 봉투 키와 **다른 salt의 scrypt**라서, 해시가 새어도 봉투는 안 열린다.
- 로그인 세션: 쿠키 `s.<비밀>` ↔ 서버에는 해시와 "그 비밀로 잠근 데이터 키"만(`lib/auth-store.ts`, `auth.json`). OAuth 토큰과 같은 방식.
- 이메일 인증 전에는 로그인 불가. 인증·재설정 링크는 `#` 뒤에 토큰(접속 로그에 안 남음), 1회용, 각 48시간·30분.
- 비밀번호 찾기: 메일 링크 + **복구 코드**면 기록 유지. 복구 코드가 없으면 계정은 되찾되 기록은 지운다(아무도 못 여니까).
- 구글: PKCE + state 쿠키(서명), 구글이 인증한 이메일만. 같은 이메일의 이메일 계정이 있으면 합치지 않고 거절. 가입은 안내문(`app/google-notice.tsx`, 버전 `GOOGLE_NOTICE_VERSION`)에 체크해야만 진행되고 동의 기록이 남는다.
- 구글 계정이 비밀번호를 설정하면 `server` 봉투를 지운다 → 이후 구글 로그인은 "누구인지"만 확인하고, 비밀번호를 한 번 더 받아 연다(`/login?unlock=1`).
- 예전 링크 계정은 내 계정 → "이메일·비밀번호로 바꾸기"로 같은 데이터 키를 봉투에 옮기고 링크를 끈다.
- 요청 제한: 로그인 IP당 30회·이메일당 8회/15분, 메일 IP당 20회·이메일당 4회/시간.

**`VAULT_MASTER_KEY`를 잃으면** 비밀번호를 설정하지 않은 구글 계정은 기록을 못 연다. Railway 변수 외에 안전한 곳에 따로 보관할 것. 반대로 이 값과 볼륨이 함께 새면 그 계정들의 기록이 열린다(가입 안내문에 적은 위험).

### 3a. 커넥터 로그인 (OAuth 2.1)

- 주소: 모두 같은 `…/api/mcp`. 토큰 없이 부르면 `401` + `WWW-Authenticate: Bearer resource_metadata=…` → 클라이언트가 `/.well-known/oauth-protected-resource`, `/.well-known/oauth-authorization-server`를 읽고 `/api/oauth/register`(동적 등록, 공개 클라이언트)로 등록한다.
- 허용 창 `/oauth/authorize`: 참여자는 **자기 계정으로 로그인한 상태**에서만 허용할 수 있다(로그인 안 돼 있으면 `/login?next=…`로 보냈다가 돌아옴, 운영자 세션 불가). 돌아갈 주소(host)를 크게 보여준다 — 앱 이름은 앱이 스스로 밝힌 값이라 믿을 수 없기 때문. 돌아갈 주소는 등록 때 낸 것과 정확히 같아야 하고 https 또는 localhost만 된다. PKCE S256 필수.
- 열쇠 전달: 허용 순간 서버는 지금 로그인 세션이 가진 데이터 키를 그것을 **인가 코드 → 접근 토큰·갱신 토큰** 각각에서 만든 키로 봉투에 넣어 저장한다. 서버에는 각 토큰의 해시와 봉투만 남는다(`lib/oauth.ts`, `.data/oauth.json`). 그래서 OAuth도 "운영자는 못 연다"를 그대로 지킨다.
- 수명: 코드 5분·1회용(실패해도 소진), 접근 토큰 1시간, 갱신 토큰 60일·쓸 때마다 교체.
- 끊기: 내 계정 → 연결된 앱, 링크 재발급, 링크 중지, 탈퇴 시 전부 즉시 폐기.
- 커넥터가 돌려주는 대시보드 주소는 이제 토큰 없는 `https://…/`라서 Claude 대화 기록에도 열쇠가 남지 않는다.

### 남은 한계 (참여자에게 정직하게 알릴 것 — `/privacy` 3항에 적어둠)

| 한계 | 왜 | 해결 방향 |
|---|---|---|
| 예전 형식 커넥터 주소(`/api/mcp/<토큰>`)는 접속 로그에 남는다 | 경로에 토큰이 있음 | 기본 주소는 OAuth(`/api/mcp`, 토큰은 `Authorization` 헤더)로 바꿨다(§3a). 예전 형식은 OAuth를 못 쓰는 도구용으로만 내 계정에 접어서 경고와 함께 보여준다. 쓰는 사람이 없어지면 경로를 막는다. |
| 운영자가 코드를 바꿔 배포하면 키를 가로챌 수 있다 | 서버가 요청 중에 키를 만들기 때문 | 배포는 공개 저장소 커밋에서만, Railway 배포 기록 보존, 가능하면 배포 권한을 다른 사람과 나누기. 근본 해결은 브라우저/클라이언트 쪽 암호화(E2E)인데, Claude가 서버 도구로 기록하는 구조와 맞지 않는다. |
| 요청 처리 중에는 평문이 메모리에 있다 | 회로 검사·CAD 생성을 서버가 한다 | 수용. 평문을 로그에 쓰지 않는다(에러 로그는 메시지만). |
| 별명·가입일·연결한 프로그램 이름은 평문 | 운영자가 계정을 관리해야 함 | 별명에 실명을 쓰지 말라고 가입 화면에서 안내 |
| 링크를 잃으면 기록 복구 불가 | 위 설계의 대가 | 가입 직후 저장 확인 체크, 내 계정 → 내보내기 |

### 왜 스크립트 CSP(`script-src`)는 아직 없나
Next.js는 인라인 스크립트를 쓰므로 nonce 방식 CSP가 필요하고, 그러면 모든 페이지가 동적 렌더링이 된다 (`node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md`). 지금은 프레임·폼·base·object 제한만 걸었다. 공개 규모가 커지면 proxy에서 nonce CSP를 붙인다.

## 5. 운영 체크리스트 (배포 전)

- [ ] `APP_PASSWORD` 20자 이상 무작위, `SESSION_SECRET` 32바이트 이상 무작위 (둘은 다른 값)
- [ ] `NODE_ENV=production` (쿠키 `Secure`, HSTS)
- [ ] `APP_BASE_URL`을 실제 주소로 (Origin 검사·링크 생성 기준)
- [ ] Railway 계정 2FA, 프로젝트 멤버 최소화
- [ ] Railway 볼륨 백업 켜기 (백업도 암호문이지만 users.json의 별명은 평문)

## 6. 사고 대응

| 상황 | 할 일 |
|---|---|
| 참여자가 링크 유출 신고 | 참여자가 직접 내 계정 → 새 링크. 못 하면 운영자가 **링크 중지**(기록은 남지만 아무도 못 엶) 후 새 계정 안내 |
| 운영자 비밀번호 유출 | Railway 변수 `APP_PASSWORD`, `SESSION_SECRET` 교체 → 모든 운영자 세션 무효(참여자 영향 없음) |
| 볼륨 파일 유출 | 참여자 기록은 암호문. 별명 목록 유출 사실을 참여자에게 알림. 개인정보 유출 신고 기준(개인정보 보호법 34조) 검토 |
| 남용 계정 | 링크 중지 → 필요 시 기록 삭제. 감사 로그(`audit.jsonl`)에 남음 |
